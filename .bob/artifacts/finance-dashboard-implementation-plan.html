React Market Dashboard: Implementation Plan

IBM and up to four competitors · Yahoo Finance data · Day, 7-day and quarter views

Summary. Build a Vite + TypeScript React app backed by a thin Express proxy that wraps yahoo-finance2. The UI talks only to /api/*. TanStack Query manages server state, Carbon Charts renders rebased comparison lines, and a fixture provider keeps tests and demos independent of Yahoo. Work lands as small PRs, each tied to a GitHub issue.

1. Repository starting point

The repository contains workshop documents only: README.md, two workshop guides, a CI workflow, a PR template and one example feature request. There is no package.json, .gitignore or application code. The app is built at the repository root because the existing CI and PR template assume a root package.json.

2. Key decision: backend proxy

Yahoo Finance has no official public API and does not provide browser CORS access. yahoo-finance2 is a Node library. A proxy is therefore required for reliability.

  • Proxy: fetches, normalizes, caches and returns a stable JSON contract.
  • React app: never imports yahoo-finance2.
  • Provider interface: YahooProvider for live data and FixtureProvider for tests, demos and offline use.

4. Data contract and services

Provider interface (server)

interface MarketDataProvider {
  getQuotes(symbols: string[]): Promise<RawQuote[]>;
  getHistory(symbol: string, range: HistoryRequest): Promise<RawBar[]>;
  searchSymbol?(q: string): Promise<SymbolHit[]>;   // used in Part 2
}

MarketDataService maps windows to intervals, normalizes output to { symbol, currency, points[{t, close}], previousClose }, drops and flags missing bars, and applies a TTL cache with request de-duplication.

ViewYahoo requestNotes
Current day5m bars from the start of the latest sessionOn weekends or closed markets, fall back to the last trading session and label it
Last 7 days1h (or 30m) bars over 7 calendar daysCovers about 5 trading days
Last quarter1d bars over trailing ~90 daysAssumed definition; recorded in an ADR

API surface

  • GET /api/quotes?symbols=IBM,MSFT,...
  • GET /api/history?symbol=IBM&window=day|week|quarter
  • GET /api/history/compare?symbols=...&window=... (one batched call per view)

Client

api/client.ts wraps fetch with an AbortSignal timeout, parses every response with the shared zod schema, and throws typed ApiErrors. domain/ holds pure functions with no React or network dependency: toPercentChange, rebaseToHundred, rankBy, computeWindowChange.

6. Charting approach

  • Library: @carbon/react with @carbon/charts-react for IBM design consistency and accessibility. Fall back to Recharts if the first spike finds React 19 or Vite incompatibility.
  • Day: summary cards plus an intraday multi-line chart.
  • Week: multi-line chart of percent change rebased to 0%.
  • Quarter: line or area chart rebased to 100, plus a ranking table.
  • Rebasing is required because the companies trade at very different price levels.
  • Accessibility: a data table or text summary per chart, and series that differ by more than color.

No Redux or Zustand until a concrete need appears. The Part 2 selected-company feature adds one piece of UI state and one query key.

8. Error handling

Server

  • Typed errors: UPSTREAM_UNAVAILABLE, SYMBOL_NOT_FOUND, RATE_LIMITED, BAD_REQUEST.
  • Clients get generic messages only. Stack traces and upstream details are logged server-side as structured JSON without sensitive data.
  • All outbound calls have timeouts.
  • Zod allowlist validation: symbol regex ^[A-Z.\-]{1,10}$, window enum, maximum 5 symbols.

Resilience

  • Promise.allSettled per symbol: one failing competitor shows an inline unavailable card, not a broken page.
  • Stale cache fallback flagged stale: true, with a "Data as of ..." banner.

Client

  • Per-card ErrorPanel with retry, a top-level ErrorBoundary, and a distinct EmptyState for market closed or no data.
  • Offline fixture mode via VITE_DATA_MODE=fixture.

npm audit --omit=dev
VITE_DATA_MODE=fixture npm run dev     # offline demo
npm run dev                            # live Yahoo via proxy

Success criteria:

  • Lint, typecheck, tests and build exit 0.
  • No high or critical audit findings.
  • All three tabs render for IBM plus four peers.
  • Stopping the proxy shows error panels, not a blank page.
  • Fixture mode works with no network.

npm run validate chains these checks, and CI runs the same command.

11. Security and dependencies

  • The server binds explicitly to 127.0.0.1, with helmet, a rate limit and a CORS allowlist limited to the Vite dev origin.
  • No secrets in the repository. .env is git-ignored and .env.example is committed.
  • Commit the lockfile; enable Mend or Dependabot; re-check yahoo-finance2 maintenance at install time.
  • If containerized later: registry.redhat.io UBI minimal base, non-root USER, read-only root filesystem.

12. Supporting GitHub-driven evolution

Design for extension

  • Add a company: edit config/companies.ts only.
  • Add a data source: implement MarketDataProvider; no UI change.
  • Add a view: add a views/*View and one tab entry.
  • Add a chart: compose LineChartAdapter.
  • The Part 2 "user-selected company graph" is pre-provisioned with SymbolPicker, symbol validation and useHistory(symbol, window). It lands as one component, one hook usage and one test file, with the existing views untouched.

Repository scaffolding

  1. .github/ISSUE_TEMPLATE/feature.yml and bug.yml with Problem, Acceptance criteria (checkbox list), Affected area (ui / server / domain / ci) and Test expectations. Structured issues map cleanly to the diff in /review --issue-coverage.
  2. Labels: feature, bug, bob-ready, needs-design, area:*.
  3. CODEOWNERS and branch protection on main with the validate check required.
  4. PR template additions: Closes #N, link to acceptance criteria, npm run validate output.
  5. docs/architecture.md and short ADRs (why a proxy, why rebasing, quarter definition).
  6. An AGENTS.md or Bob rules file stating the folder map, the "presentational components never fetch" rule, the "new data goes through shared zod schemas" rule, test expectations and branch names (feature/, fix/, bob/, matching the CI triggers).
  7. Keep issues small and single-layer so diffs stay reviewable.

Flow

Issue with acceptance criteria
   -> Branch feature/...
   -> Bob: plan, implement, add tests
   -> npm run validate
   -> PR (Closes #N, template completed)
   -> GitHub Actions runs the same validate
   -> Human review and merge

Bob handles implementation, validation and PR text. A human or separate automation performs the merge.
